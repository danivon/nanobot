# 二次开发方向（创意收集）

> 仅供参考，用于收集创意，不是开发规划。这里的方向不代表已排期、已承诺或必须实施；实际优先级应结合需求、成本和维护负担重新评估。

## 选型原则

- 优先通过 Skill、MCP、独立 Tool 或 Agent Plugin 实现，尽量不改 `nanobot/agent/loop.py`、`nanobot/agent/runner.py`、`nanobot/session/` 和安全策略。
- 先做有明确输入输出的垂直闭环，不先做“万能助手”平台。
- 优先本地可测试、可回滚、数据可控的方案；外部账号和密钥只通过配置或环境变量提供。
- 每个方向先定义最小可用能力和验收方式，再决定是否继续扩展。

## 方向概览

| 方向 | 价值 | 实现方式 | 核心改动 | 难度 |
|---|---|---|---|---|
| 本地知识库 / RAG | 很高 | MCP server + Skill | 无 | 中 |
| 每日简报 / 收件箱整理 | 很高 | Cron + MCP + Skill | 无 | 中高 |
| 会议与语音纪要 | 高 | 转写 + MCP + Skill | 无 | 中 |
| 研发项目管家 | 高 | GitHub/GitLab MCP + Subagent + Skill | 无 | 中 |
| 个人 CRM / 跟进提醒 | 中高 | 本地 SQLite Tool/MCP + Cron | 无 | 低中 |
| Agent 观测与评测 | 对开发者很高 | CLI/WebUI 扩展 | 很低 | 中高 |

## 1. 本地知识库 / RAG

把 Obsidian、PDF、Word、网页收藏等资料整理成本地知识库，提供 `kb_ingest`、`kb_search`、`kb_answer` 等工具，重点是增量索引、来源引用和 workspace 隔离，而不是简单全文搜索。

这个方向可以完全放在 `extensions/` 中实现，通过 MCP 或 Tool 接入，不依赖修改智能体核心。建议先支持一种数据源，例如 Obsidian vault 或 PDF 目录，再逐步增加来源类型。

最小闭环可以定义为：导入资料、按语义检索、基于检索结果回答并给出可追溯引用。验收时重点检查引用是否准确、无关资料是否被排除、重复导入是否幂等。

## 2. 每日简报 / 收件箱整理

用 Cron 或 Heartbeat 定时汇总日历、邮件、RSS、GitHub 通知和待办，生成“今天需要关注什么”的简报，并通过 WebUI 或聊天渠道推送。

MCP 负责连接外部数据源，Skill 负责整理规则和输出格式。建议先接 RSS 和 GitHub 这类只读数据源，再考虑邮件和日历等包含敏感信息的来源。

最小闭环可以定义为：定时拉取、去重、排序、生成摘要并标记需要人工处理的事项。验收时重点检查重复推送、时区、失败重试和敏感信息脱敏。

## 3. 会议与语音纪要

录音转写后做说话人区分、议题提取、行动项和负责人识别，并把行动项写入工作区或提醒系统。现有转写能力可以作为输入，扩展的重点是“会议结构化”和“后续跟进”。

这个方向适合用 MCP server 封装音频处理和结构化输出，再用 Skill 规定纪要模板和行动项格式，避免把处理逻辑塞进核心循环。

最小闭环可以定义为：输入音频、生成带时间戳的纪要、提取行动项并创建提醒。验收时重点检查长音频、多人说话、噪声环境和隐私数据的存储位置。

## 4. 研发项目管家

面向自己的仓库做 Issue 分类、PR 摘要与风险提示、测试失败归因、依赖升级检查等工作。用 GitHub/GitLab MCP 获取仓库信息，用 Skill 固定评审流程，复杂任务交给 Subagent。

这个方向与日常开发直接相关，但要注意不要把“自动改代码并推送”作为第一步。建议先做只读分析，再逐步增加需要人工确认的写操作。

最小闭环可以定义为：读取 Issue 或 PR、生成结构化分析、标出风险和待确认问题。验收时重点检查权限边界、误判成本和敏感信息泄露。

## 5. 个人 CRM / 跟进提醒

记录联系人、承诺过的事情、上次沟通时间和下一步动作，定期提醒跟进。用本地 SQLite 保存数据，用 Tool 或 MCP 提供增删改查，用 Cron 触发提醒。

这个方向代码量不大，但长期使用价值高，适合作为熟悉扩展机制的第二个项目。数据应默认保存在本地，并明确导出和备份方式。

最小闭环可以定义为：创建联系人、记录互动、设置跟进时间、到期提醒。验收时重点检查时区、重复提醒、数据迁移和删除行为。

## 6. Agent 观测与评测

记录每次会话的工具调用、延迟、token 成本、失败原因和最终结果，做本地回放和回归评测面板。这个方向主要服务于二次开发本身，帮助你判断改动有没有让智能体变差。

可以先从日志解析和 CLI 报表开始，再考虑 WebUI 面板。评测用例应覆盖真实可达路径，避免只测内部状态或假设场景。

最小闭环可以定义为：导入会话记录、生成调用链和成本报表、对比两个版本的评测结果。验收时重点检查数据量增长、日志脱敏和评测结果的可复现性。

## 暂不建议优先做

- 直接修改 `agent/loop.py`、`agent/runner.py`、`session/` 或安全策略，除非现有扩展点确实无法满足需求。
- 一开始就做完整的新聊天渠道，渠道包涉及配置、依赖、UI 和生命周期，维护成本较高。
- 一开始就做“全能个人助理平台”，容易同时引入权限、数据源、调度和 UI 问题，难以验证最小闭环。
